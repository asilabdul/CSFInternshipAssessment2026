# FarmTracker Code Review Audit

I would fix the paddock assignment logic first because it can silently corrupt the farm overview. `POST /api/animals` increments `animal_count` before verifying that the paddock exists, and `PUT /api/animals/:id` increments the new paddock when an animal moves but never decrements the old one. Over time the paddock capacity cards become untrustworthy, especially if animals are moved between paddocks or assigned to invalid IDs. Deleting an animal does decrement the current paddock, but that only handles one path through the lifecycle.

The second priority is API correctness and validation. `GET /api/animals` treats `page` as the SQL offset, so page 2 overlaps page 1 instead of starting after `page * limit` records. Animal creation returns `200` rather than `201`, while validation responses are inconsistent across the app. Paddocks accept non-positive capacity, animals can be assigned to nonexistent paddocks, and health events only check presence of required fields. These issues are small individually, but they make the API harder for the frontend and tests to rely on.

The missing weight tracking feature is a clear product gap and needs both a schema addition and UI work. I would implement it in the existing Express route style to keep the change reviewable, with tests covering creation, validation, unknown animals, and descending history order.

The largest architectural concern is that database schema, connection lifecycle, and table creation are all bundled into `db.js` with `CREATE TABLE IF NOT EXISTS`. That is fine for a prototype, but it gives no migration history or reliable way to evolve existing databases. The repository also tracks SQLite database artifacts, which can hide seed/setup problems and create noisy diffs. I would leave a full migration framework for later unless this app were moving toward production, but I would document a concrete migration plan and keep the current changes small enough for the assessment.
