# Retrospective

I kept the solution inside the existing Node, Express, and SQLite stack because the app is small and the assessment is about improving inherited code rather than replacing it. The main trade-off was choosing targeted fixes over a larger route/service/database refactor. That kept the changes easy to review and let the new weight feature reuse the existing patterns, but it means validation and persistence logic still live together in the route files.

I fixed the data consistency problems that could mislead users: overlapping animal pagination, incorrect create status, invalid paddock assignment, and paddock counts drifting when animals move. I also removed the tracked SQLite database artifacts and documented a migration path instead of introducing a migration framework in the same pass. That felt like the right boundary for this prototype because a half-finished migration layer would create more risk than value.

With more time, I would split the backend into route, validation, and repository modules and add centralized error handling so validation rules are not scattered across each handler. I would add browser-level end-to-end tests for the frontend and implement the migration proposal so future schema changes are explicit and reversible. The weight feature UI currently re-fetches all weights on every submission, which is fine at this scale but would need pagination or virtual scrolling for animals with hundreds of records. I deliberately left the plain HTML frontend in place; it is sufficient for the current workflow, and replacing it with a framework would not improve the core assessment outcomes.
